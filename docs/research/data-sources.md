## 访问控制与恢复

- 原探测阶段：串行，至少10秒加少量随机间隔，每供应商20次/日、合计30次/日，每轮最多10次。
- 正式阶段：基于批量接口进入全量准备，当前合计400次/日、至少间隔10秒。继续使用同一个`backend/.source-probe/state.json`和锁，已有次数、间隔、冷却不清零。初次与增量任务均受此限额。
- 登录、实际查询、SDK隐含分页与实际退出发包均计次；成功缓存复用不发送新请求，保留原保存时间。重启或新建任务不能清空额度。
- 明确HTTP403/418/429至少停止24小时，并遵守更长Retry-After；连接失败、无响应及无法确认格式的响应采用保护性暂停。
- 正常成功数据流中断，与拒绝访问区分：同一只读分块最多3次持久化短退避（30/60/120秒），完整成功后清除此块连续失败计数；仍受全局最小间隔和日预算约束。连续失败停止短重试，交回保护性恢复。
- 无代理池、换IP、自动重定向或伪造身份。源限制不会因数据尚未齐全而绕过。

先前腾讯正常原价回退曾被本地格式检查误判；通过原价与回退报文逐条相同、SHA256及冷却时间绑定纠正，保留其他限制和全部次数。另一次SDK大包在旧20秒总上限被本地中断，原始流已收到约90%，据证将接收窗口改为120秒。此类纠正均写入账本审计，未把半包当作完整数据。

## 证据与验收层次

公开原文和探测报告位于不入Git的`backend/.source-probe/`；正式成功SDK响应在`backend/.state/baostock-wire/`，腾讯原文在`backend/.state/source-cache/`。失败半包只作诊断，不进入成功缓存或业务行情。

目录计数、小样本、隔离PostgreSQL回归、正式全量发布是不同层次。真实HTTP已完成初始化、分类与首次全量发布，全部所需输入通过后才发布；正式验收结果见[后端说明](../../backend/README.md)。

最新快照可使用构建时已取得的分类，并单独标注分类资料截至时间；不能把该时间解释为行情日已知。历史回补采用当时已有的分类，缺失时未知。

## 维护命令

在仓库根目录通过uv执行。预览或离线复核不会访问上游：

```bash
uv run --project backend --frozen python backend/tools/probe_sources.py --date 2026-10-30 --source sina --group catalog
uv run --project backend --frozen python backend/tools/probe_sources.py --date 2026-10-30 --source tencent --group history --offline
```

正式取数后不要并行运行其他采集器叠加访问。维护入口`check-source`、`check-tencent-metadata`同样使用正式共享账本；其成功不替代正式发布验收。Schema审计、部署及完整HTTP流程见[部署说明](../deployment/backend.md)。
