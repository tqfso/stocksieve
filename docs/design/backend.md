# 后端概要设计

当前落地范围：沪深四板块、当前服务器单机Docker、真实前后端接口；AI使用后端模拟。北交所后续补齐，具体数据与验收结果以[后端指南](../../backend/README.md)为准。

本文确定模块职责、数据流和关键取舍；接口字段、策略公式及表结构分别以 [API](../api/README.md)、[策略设计](../product/strategies/README.md)和 [SQL](../../backend/sql/init.sql)为准，不在此重复。

## 1. 约束与技术方向

- 部署在当前服务器，用户少，采用单体代码库，按职责拆分运行进程。
- 股票、分类和财务资料只使用免费渠道；缓存、增量获取与保守限频优先，覆盖不足如实展示。
- AI 服务可配置地址、模型、密钥及 `chat_completions` / `responses` 协议，兼容服务分别配置实际支持的协议；不预设某家支持两种接口。股票免费数据约束不代表模型调用免费。
- 使用 Python 3.12、aiohttp、Pydantic、SQLAlchemy 和 PostgreSQL，依赖与虚拟环境统一由 uv 管理；V1 不增加 Redis 或独立消息队列。

## 2. 模块职责

| 模块 | 职责 |
| --- | --- |
| `identity` | 账号、密码、会话及权限 |
| `market` | 证券与日线模型、前复权、K线、五类策略和不可变快照查询 |
| `ingestion` | 渠道端口与注册、供应商适配、频控缓存、初始化及收盘快照构建发布 |
| `jobs` | 任务受理、幂等、租约、恢复、worker与调度 |
| `analysis` | 财务与筹码计算、分析用例、报告契约、智能体及模拟运行适配 |

同一模块的业务逻辑由 API 和后台任务共用；API 不执行长耗时采集与模型调用。

源码采用业务分包，模块内部按实际职责设置分层，不建立空目录占位：

```text
stocksieve/
  bootstrap/                 启动命令与依赖组装
  interfaces/http/           路由、HTTP校验和响应
  modules/
    identity/                账号模块
    market/                  行情与策略模块
    ingestion/               同步与数据源模块
    jobs/                    任务模块
    analysis/                AI分析模块
  infrastructure/persistence/ 连接、表定义、通用写入和结构审计
  shared/                    基础类型、配置、时间和序列化
  operations/                运维验收流程
```

- `domain`：`Stock`、`Bar`、`StockState`及租约值对象、策略和计算规则；不依赖Web、数据库或供应商SDK，核心规则采用轻量DDD建模。
- `application`：用例、输入/输出契约、事务和跨模块协调。保留适合当前规模的SQLAlchemy短事务脚本，连接、表结构和通用持久化操作集中复用。
- 模块内`infrastructure`：行情供应商、网络传输及智能体框架的具体适配器，实现应用层端口。由`bootstrap`组装，应用服务不创建具体外部客户端。

依赖方向为HTTP接口→应用→领域；应用可使用共享持久化设施。模块间使用显式应用服务或端口，目录边界由自动化测试检查。根目录仅保留包标识和兼容的`stocksieve.cli`入口。

## 3. 运行形态与数据流

PostgreSQL、API、worker、scheduler统一由`backend/compose.yaml`管理；三个应用进程共用后端镜像，编译前端由API同源提供。worker的同步队列和分析队列分开领取，各一个执行名额。scheduler只登记到期任务，不采集数据。

```text
浏览器 → API → PostgreSQL（会话、任务、幂等记录、快照、报告）
                    ↑               ↑
             scheduler 登记任务    worker 执行任务
                                    ↓
                       数据渠道 / 指标策略 / AI 服务
```

核心流程：

1. 基础数据：初始化只更新股票基础信息；行业、题材和归属由独立分类任务更新，两者分别记录成功时间。交易日历由行情渠道维护，分类失败或尚未同步不阻塞行情。
2. 收盘同步：固定目标日期、覆盖板块和历史配置 → 就绪预检 → 补齐近期行情 → 校验/复权/策略计算 → 事务发布 → 独立任务补齐较早历史。env统一配置首次补齐天数和最大历史天数，当前为150/2500，约十年；上市较晚的证券从实际可得行情开始。频控等待跨日恢复，历史回补不阻塞已发布策略，旧快照和报告资料保留。
3. 浏览：列表解析确定快照，详情、图表和分析沿用该快照；未发布数据不可见。
4. 分析：固定用户、股票、快照和策略 → 加载分析技能 → 按需联网检索、读取原文并调用计算工具 → 校验并保存结构化报告；后续可由同一报告生成文档。

具体调度和发布规则沿用 [同步约定](../api/common/sync-policy.md)与[快照约定](../api/common/snapshots.md)。

## 4. 数据渠道与频控

- 每次更新选择一个支持该任务的数据源，执行与重试沿用该渠道；不可用时明确失败。
- 业务层通过统一接口取数，各渠道适配器负责请求和数据格式转换。新增渠道通过实现接口并注册接入。
- 分类渠道可独立选择；只更新该渠道提供的类别，其余已有分类保留。批量采集按任务恢复，优先当前候选股，覆盖范围和实际获取时间随快照冻结。
- 当前采用明示组合：Baostock提供沪深行情、日历、行业与除权参考价，腾讯提供市值及新增编码的明确板块标签；价格和复权始终使用同一价格上游，字段来源随快照保存。
- 题材使用独立百度股市通渠道，按股票批量取得明确概念，分批补齐后通过新行情快照生效。
- 所有对同一供应商的实际请求共用限频和冷却机制；遇到限流暂停访问，重试次数受限。
- 正式同步沿用访问账本，默认共享1秒间隔、项目预算1000次/日，预留最多100次给日常更新；日常任务优先，历史回补使用剩余额度并可跨日恢复。参数由本项目设定，遇上游限流暂停；不清空旧次数或真实冷却，缺失资料保持未知。

渠道能力、实测结果和探测参数见[免费数据源验证](../research/data-sources.md)。

## 5. 数据存储与一致性

沿用现有 17 张表：账户与会话、证券与分类、交易日历、任务、快照与日线修订、策略信号、任务日志与调度触发、幂等请求、财报、分析资料及结果。初始化 SQL 维护完整结构；结构变更按[项目数据库约定](../../AGENT.md#数据库约束)同步更新已部署数据库。

- 保存未复权 OHLC、原始成交量/额和复权因子；按快照日期统一前复权。缺失值保留 `null`，单位在渠道边界转换。
- 日线以“快照 + 股票 + 日期”保存修订；读取时只解析该快照版本可见的最新修订。发布时冻结历史范围、复权、分类及策略版本，避免新数据改写旧页面。
- 构建过程可分批落库，发布使用短事务，保证行情与策略结果一同可见。失败快照不改变最新有效快照。
- 保留可复查的来源、获取时间、披露时间和财报口径。历史行情快照与随后取得的财务资料时间分别展示，禁止将后取得资料解释为历史已知信息。
- 最新收盘研究可采用构建时已取得的分类，单独显示分类资料截至时间；历史回补只采用当时已取得的分类。任务及快照冻结覆盖范围，后续扩展北交所不改写旧范围。
- 快照保存和失败构建清理策略待全市场容量测算后确定，不提前删除被历史报告引用的数据。

## 6. 后台任务与恢复

沿用 [任务契约](../api/common/tasks.md)，以数据库任务表作为持久化队列。

- 领取时用短事务锁定到期任务并写入租约；长任务续租，完成写入校验租约归属，防止旧 worker 覆盖新执行者。
- 进程异常退出后回收过期租约，按任务阶段恢复；批次写入幂等，不能只把状态改回排队后重复产生业务结果。
- 同步任务串行，分析按用户和输入范围去重；提交幂等记录与任务创建在同一事务提交。
- 等待行情或频控时保存下次执行时间并释放执行名额；限流熔断不可通过重建任务绕过。
- 数据就绪超时与网络失败分别记录；用户退出、关闭页面或会话过期不取消已受理任务。
- 网络故障最多恢复检查3次，期间仍遵守真实冷却；SDK空闲连接被动检查及重建同样计入请求预算。

## 7. AI 与权限边界

- 当前按用户安排默认使用模拟运行层，不需要模型凭据或联网查询；复用现有任务、计算、报告和权限链路，任务及报告永久保存模拟标识。基本面缺财报时只生成说明缺失的模拟内容，筹码与参考价仍由实际输入计算。后续显式切换真实模式，不因模型故障自动生成模拟结果。
- 采用“智能体框架 + 本地技能 + 工具适配”的结构，使用已锁定的 DeepAgents、LangGraph 和模型适配SDK；已验证框架构图及技能加载，真实服务的协议兼容性仍需验证。
- 首版提供一个股票分析技能，以 `SKILL.md` 和配套资料维护基本面、筹码及买卖建议的分析方法和报告要求。技能由运行层加载，工具权限与执行限制由后端管理。
- 联网通过可替换的检索和网页读取工具提供，供智能体按需查询公告、财报及相关新闻；优先采用交易所、公司公告等原始资料，保留引用原文及来源时间，取得资料不足时明确说明。
- 模型适配层分别支持 Chat Completions、Responses；逐服务验证工具调用能力，能力受限时采用预先准备资料的生成流程。工具复用已有数据渠道和频控，运行次数、超时和费用设上限。
- 财务指标、策略条件和筹码估算由代码或核验来源提供，模型组织分析；报告通过结构校验，来源引用实际资料，并保留技能、模型与计算版本。
- 后续文档功能基于已保存的结构化报告和图表，用模板生成 Markdown、Word 或 PDF；生成结果关联原分析及输入版本，沿用报告所属用户的访问权限。

三类分析内容见[AI分析设计](../product/ai-analysis-design.md)。前端已改用服务器会话、行情、图表、队列及报告接口；浏览器不生成业务数据或分析报告。

技能在独立临时工作区加载，完整正文固定加入本次分析上下文；模型不具备服务器命令执行权限。SDK测试不等于真实模型联调，报告文档导出仍为后续扩展。

密码使用成熟哈希库，会话令牌服务端可撤销、数据库只保存摘要。后端执行角色和资源归属校验，管理员也不能读取他人分析报告。密钥通过服务器配置注入，日志不写密钥、密码或会话令牌。

## 8. 部署与验证

后端使用本机ubuntu:24.04及uv锁定依赖；统一Compose沿用PostgreSQL15镜像和原有持久化卷。API默认监听本机8000端口并同源提供前端。首次合并旧部署时先备份、验证容器身份与数据卷，再迁移控制权并核对业务行数；结构直接对齐、不重建已有库。配置统一放在`backend/.env`。

验证覆盖真实PostgreSQL与HTTP、浏览器端到端、策略边界与无未来数据、覆盖范围与单位、幂等权限、恢复和限频。隔离测试不写业务表；真实初始化及发布另行通过正式服务验收，二者分别记录。

## 9. 实现顺序与待定项

基础工程、账号、任务、快照策略、真实接口与浏览器链路均已实现。正式服务已完成沪深四板块的真实首次补齐和发布；之后持续观察增量时长、源稳定性与存储占用。

后续项：北交所完整免费覆盖、更多分类来源、实际AI联网与模型联调及报告文档导出。AI模拟、四板块先上线和免费数据约束均已由用户确认。
