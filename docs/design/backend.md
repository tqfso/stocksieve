# 后端概要设计

当前落地范围：沪深四板块、当前服务器单机Docker、真实前后端接口；AI统一调用真实模型。北交所后续补齐，具体数据与验收结果以[后端指南](../../backend/README.md)为准。

本文确定模块职责、数据流和关键取舍；接口字段、策略公式及表结构分别以 [API](../api/README.md)、[策略设计](../product/strategies/README.md)和 [SQL](../../backend/sql/init.sql)为准，不在此重复。

## 1. 约束与技术方向

- 部署在当前服务器，用户少，采用单体代码库，按职责拆分运行进程。
- 股票、分类和财务资料只使用免费渠道；缓存、增量获取与保守限频优先，覆盖不足如实展示。
- AI 服务可配置地址、模型、密钥及 `chat_completions` / `responses` 协议，兼容服务分别配置实际支持的协议；不预设某家支持两种接口。股票免费数据约束不代表模型调用免费。
- 使用 Python 3.12、aiohttp、Pydantic、SQLAlchemy 和 PostgreSQL，依赖与虚拟环境统一由 uv 管理；V1 不增加 Redis 或独立消息队列。

## 2. 模块职责

| 模块 | 职责 |
| --- | --- |
| `identity` | 账号、密码、会话及权限 |
| `market` | 证券与日线模型、前复权、K线、五类策略和不可变快照查询 |
| `ingestion` | 渠道端口与注册、供应商适配、频控缓存、初始化及收盘快照构建发布 |
| `jobs` | 任务受理、幂等、租约、恢复、worker与调度 |
| `analysis` | 财务与筹码计算、统一报告用例、报告与引用契约、Word/PDF导出端口、模型运行适配 |

同一模块的业务逻辑由 API 和后台任务共用；API 不执行长耗时采集与模型调用。

源码采用业务分包，模块内部按实际职责设置分层，不建立空目录占位：

```text
stocksieve/
  bootstrap/                 启动命令与依赖组装
  interfaces/http/           路由、HTTP校验和响应
  modules/
    identity/                账号模块
    market/                  行情与策略模块
    ingestion/               同步与数据源模块
    jobs/                    任务模块
    analysis/                AI分析模块
  infrastructure/persistence/ 连接、表定义和通用写入
  shared/                    基础类型、配置、时间和序列化
```

- `domain`：`Stock`、`Bar`、`StockState`及租约值对象、策略和计算规则；不依赖Web、数据库或供应商SDK，核心规则采用轻量DDD建模。
- `application`：用例、输入/输出契约、事务和跨模块协调。保留适合当前规模的SQLAlchemy短事务脚本，连接、表结构和通用持久化操作集中复用。
- 模块内`infrastructure`：行情供应商、网络传输及智能体框架的具体适配器，实现应用层端口。由`bootstrap`组装，应用服务不创建具体外部客户端。

依赖方向为HTTP接口→应用→领域；应用可使用共享持久化设施。模块间使用显式应用服务或端口，包根目录仅保留标识，运行入口由`backend/run.py`加载`bootstrap.cli`。

## 3. 运行形态与数据流

PostgreSQL、API、worker、scheduler统一由`backend/compose.yaml`管理；三个应用进程共用后端镜像，编译前端由API同源提供。worker的同步队列和分析队列分开领取，各一个执行名额。scheduler只登记到期任务，不采集数据。

```text
浏览器 → API → PostgreSQL（会话、任务、幂等记录、快照、报告）
                    ↑               ↑
             scheduler 登记任务    worker 执行任务
                                    ↓
                       数据渠道 / 指标策略 / AI 服务
```

核心流程：

1. 基础数据：初始化只更新股票基础信息；行业、题材和归属由独立分类任务更新，两者分别记录成功时间。交易日历由行情渠道维护，分类失败或尚未同步不阻塞行情。
2. 收盘同步：固定目标日期、覆盖板块和历史配置 → 就绪预检 → 补齐近期行情 → 校验/复权/策略计算 → 事务发布 → 独立任务补齐较早历史。env统一配置首次补齐天数和最大历史天数，当前为150/2500，约十年；上市较晚的证券从实际可得行情开始。频控等待跨日恢复，历史回补不阻塞已发布策略，旧快照和报告资料保留。
3. 浏览：列表解析确定快照，详情、图表和分析沿用该快照；未发布数据不可见。
4. 新版分析目标：固定用户、股票和行情版本 → 准备数据库指标及筹码 → 按需获取行业与公司资料 → 统一分析 → 校验并保存结构化报告及引用。筹码独立查询，Word/PDF均从已保存报告导出。

具体调度和发布规则沿用 [同步约定](../api/common/sync-policy.md)与[快照约定](../api/common/snapshots.md)。

## 4. 数据渠道与频控

- 新浪更新证券基础、上市日期、板块、日历、行情、复权及新收盘数据市值；百度更新行业和题材。
- 每次任务固定一个逻辑渠道，价格和因子同源；业务依赖能力接口，新增渠道通过独立适配器注册。
- 日常更新优先采用批量当日报价并核验官方因子，只补最新交易日；缺历史、日期断档或历史因子修订时回查保留窗口。历史回补沿用原策略快照范围和当日状态。
- 同日期、渠道、配置和分类已有成功结果时直接复用；分类或历史配置变化时重新发布，运维可显式强制重算。人工失败重试沿用原任务和检查点。
- 共享最小0.2秒请求间隔、项目预算20000次/日，80%为日常更新预留；百度分类至少间隔1秒。实际访问、预算和冷却跨重启保留，遇限流暂停。

金额及市值统一为元、成交量为股；新浪累计因子统一转换为前复权。百度优先采用申万一级，仅有国标时明确标注。缺失字段保持未知，不用其他渠道价格拼接。

## 5. 数据存储与一致性

沿用现有 17 张表：账户与会话、证券与分类、交易日历、任务、快照与日线修订、策略信号、任务日志与调度触发、幂等请求、财报、分析资料及结果。初始化 SQL 维护完整结构；结构变更按[项目数据库约定](../../AGENT.md#数据库约束)同步更新已部署数据库。

- 保存未复权 OHLC、原始成交量/额和复权因子；按快照日期统一前复权。缺失值保留 `null`，单位在渠道边界转换。
- 历史接口可能返回上市以来的数据，先依据最大保留交易日范围截取再校验；范围内异常明确报出股票与日期，保留原文，不改写价格。
- 日线以“快照 + 股票 + 日期”保存修订；读取时只解析该快照版本可见的最新修订。发布时冻结历史范围、复权、分类及策略版本，避免新数据改写旧页面。
- 构建过程可分批落库，发布使用短事务，保证行情与策略结果一同可见。失败快照不改变最新有效快照。
- 保留可复查的来源、获取时间、披露时间和财报口径。历史行情快照与随后取得的财务资料时间分别展示，禁止将后取得资料解释为历史已知信息。
- 最新收盘研究可采用构建时已取得的分类，单独显示分类资料截至时间；历史回补只采用当时已取得的分类。任务及快照冻结覆盖范围，后续扩展北交所不改写旧范围。
- 快照保存和失败构建清理策略待全市场容量测算后确定，不提前删除被历史报告引用的数据。

## 6. 后台任务与恢复

沿用 [任务契约](../api/common/tasks.md)，以数据库任务表作为持久化队列。

- 领取时用短事务锁定到期任务并写入租约；长任务续租，完成写入校验租约归属，防止旧 worker 覆盖新执行者。
- 进程异常退出后回收过期租约，按任务阶段恢复；批次写入幂等，不能只把状态改回排队后重复产生业务结果。
- 新浪目录分页、元资料和报价批次按任务保存断点，频控续跑不重放已完成批次；已通过的板块预检复用，出现个股未就绪时重新检查。
- 新浪任务内复用HTTP连接；最多1秒的正常请求间隔在异步请求边界等待，额度、冷却和长等待释放执行名额后续跑。进度按已完成股票数显示，发布后才到100%。
- 人工重试沿用原任务ID、未发布快照和股票游标，保留已完成批次与错误日志；渠道、日期和配置保持冻结，检查点不完整时明确拒绝。
- 同步任务串行，分析按用户和输入范围去重；提交幂等记录与任务创建在同一事务提交。
- 等待行情或频控时保存下次执行时间并释放执行名额；限流熔断不可通过重建任务绕过。
- 数据就绪超时与网络失败分别记录；用户退出、关闭页面或会话过期不取消已受理任务。
- 网络故障最多恢复检查3次，期间仍遵守真实冷却。

## 7. AI 报告、筹码与权限边界

统一报告、独立筹码和Word/PDF已按下述边界实现。产品内容见[AI分析报告设计](../product/ai-analysis-design.md)，真实模式以配置的模型服务和巨潮原文开展研究。

- 报告面向任意已覆盖股票，不要求入选策略；任务固定用户、股票和行情版本。已入选规则作为背景，统一生成报告，不再按三种类型或策略分别生成。
- 本地资料层读取行情、均线、已同步财务和估值，并调用筹码与技术计算；联网资料层按市场注册独立适配器，交易所公告优先，资料足够即停止补源。公司与行业PE先核对口径、日期和行业分类，未知字段保持缺失。
- 筹码计算为可复用领域能力，通过独立查询提供页面图形，也为报告准备指标；无需创建AI任务或调用模型。缺少筹码只限制对应结论，不阻断其他资料的分析。
- 继续采用“智能体框架 + 一个股票分析技能 + 工具适配”，采用LangGraph显式编排。技能与报告契约统一，覆盖七项内容；指标、参考价和筹码由代码或核验资料提供，模型负责综合分析。
- 报告统一由真实模型生成，沿用任务、校验和权限；已有历史报告保留原标识。未核验信息明确标注，不能虚构公司事实或来源。公告暂缺时仍按已有行情、技术与财务生成报告。
- 联网检索按市场注册独立适配器，交易所优先，未命中再补源；公告暂缺仍基于已有资料生成分析。原文读取使用可替换适配器，所有访问共用供应商频控、缓存、预算与冷却。资料保留标题、机构、原文URL、发布时间、获取时间与引用关系；后取得的信息不解释为历史已知事实。
- 模型适配层分别支持Chat Completions与Responses协议，按服务核验工具能力，限制执行次数与超时。缺少模型配置或调用失败时明确报错。
- 报告按结构化章节、关键指标和资料引用保存，记录输入、技能、模型与计算版本，正文引用可追溯。公司基本资料包含股东户数与集中观察，行业PE归入关键指标，缺失只在相关字段和判断中提示。个人历史及进行中任务通过真实后端恢复。
- Word/PDF导出采用独立文档适配器，由已保存的选定报告生成有效.docx或.pdf；两种格式共用报告内容模型，分别处理排版，保留摘要、六章、含行业PE的关键指标、可点击引用与历史标识；不重新取数或分析，不自动附独立筹码展示页。API鉴权后返回文件，小用户量下先不增加独立文档服务。

页面、历史报告和两种导出文件均校验用户归属，管理员也不能读取他人报告。技能由后端加载为固定分析规则；模型仅可调用检索下载、文档阅读和金融计算三个工具，网页不能改变权限，也不能读取服务器文件或执行命令。密码使用成熟哈希，会话可撤销且只保存摘要；密钥从服务器注入，不写入日志或导出文件。

## 8. 部署与验证

后端使用本机ubuntu:24.04及uv锁定依赖；统一Compose沿用PostgreSQL15镜像和原有持久化卷。所有服务使用bridge网络，API内部8000映射到服务器24048并同源提供前端，应用通过postgres服务名访问数据库。初始化SQL只用于空库；结构变更直接更新已有PG并保留业务数据。配置统一放在`backend/.env`。

验证覆盖真实PostgreSQL与HTTP、浏览器端到端、策略边界与无未来数据、覆盖范围与单位、幂等权限、恢复和限频。接口测试固定使用真实PG与TCP/HTTP，测试数据写入自动清理的独立schema，不写public业务表；真实初始化及发布另行通过正式服务验收，二者分别记录。

## 9. 实现顺序与待定项

基础工程、账号、任务、快照策略、真实接口与浏览器链路均已实现。正式服务已完成沪深四板块的真实首次补齐和发布；之后持续观察增量时长、源稳定性与存储占用。

统一报告、独立筹码和Word/PDF导出已实现，接口同步更新；以PG/HTTP、浏览器及文件内容验证供用户验收。真实AI已接入公告原文阅读；结构化行业估值与股东户数资料继续补充；北交所和更多分类来源继续扩展。
